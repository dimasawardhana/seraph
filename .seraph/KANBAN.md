### TASK-119 · A task can point at the documents that explain it

> **Goal:** A task carries title, goal, description and acceptance and points nowhere, so the reasoning behind a piece of work cannot live in the document that actually holds it; each task should be able to name the repository documents it depends on.
- priority: medium
- claimed by: omp (session `omp-20261005T030418Z-01a10a04`, until 2026-10-05T12:24:23Z)
- updated: 2026-10-05T11:54:23Z

> **Done when:** 1. A task carries references: repository-relative paths, each optionally with an anchor, such as CONTEXT.md#index. [ ]
> **Done when:** 2. The references survive a round trip through the database and both snapshots unchanged, and a clone restores them. [ ]
> **Done when:** 3. create_task and update_task accept them; no new tool is added, because this is a field on a task and not a second kind of thing. [ ]
> **Done when:** 4. A reference whose file does not exist is reported by `seraph doctor`, naming the task and the path. It is NOT written into KANBAN.md, because that file must stay a pure function of the database for the snapshots to compare equal between machines. [ ]
> **Done when:** 5. The migration from schema v2 to v3 is correct on an existing board, and the migration runner can no longer re-run an older migration. [ ]
> **Done when:** 6. Tests cover the round trip, the anchor form, a missing file, and a board migrated from v2. [ ]
> **Done when:** 7. docs/USING.md, README.md and CONTEXT.md describe it, and CONTEXT.md keeps the Index reserved for what §13 says it is. [ ]
> **Done when:** 8. Done through the board with the claim held by the session that did the work. [ ]

> Asked for directly, and deliberately smaller than the Index.
> WHAT THIS IS NOT. prd.md §13 designs an Index — a searchable projection of a project's prose, FTS5, staleness by content_hash, six open questions — and ROADMAP.md carries it as not scheduled. This is a task naming documents, not a store of documents, and it does not pre-empt that design: a reference is a path today and can resolve to an index entry later without the task shape changing.
> WHAT THIS DELIBERATELY DOES NOT DO. It does not put the documents inside state.db. That database is gitignored, so documents held there would be machine-local and would vanish from a clone — which is precisely the defect TASK-116 spent an hour on, one level up. Documents stay in the repository, where git can review them, and seraph points at them.
> THE INVARIANT THAT DECIDED WHERE THE WARNING GOES. ADR-0001 makes the rendered view the product: a tool response is byte-identical to the snapshot. So KANBAN.md must be a pure function of the database. A reference check reads the filesystem, so on a clone where the document is missing the rendered board would differ from the one committed — and every clone would report DIFFERS from a board it has not touched. The dangling warning therefore lives in `seraph doctor`, which already reports snapshot freshness and reads the filesystem on purpose, and the snapshot renders the references as plain text.
> THE MIGRATION IS THE PART MOST LIKELY TO BREAK SOMETHING. Migrate currently chooses between createTasks and a single upgrade slice on `current >= 1`, and that upgrade slice holds the v1-to-v2 statements. Raising SchemaVersion to 3 without restructuring would make every existing v2 board run `ALTER TABLE tasks ADD COLUMN goal` again and fail. The runner has to become per-version, which this task does rather than working around.
